# Два поисковика: первая безопасная версия

Локальный прототип состоит ровно из двух контейнеров: `search-reflected` и
`search-dom`. В каждом работает Node.js-приложение со своим встроенным ботом
Playwright. Общие исходники приложения находятся здесь, исходники бота —
в `tasks/kb-search-bot`. Отдельного контейнера бота нет.

Это **безопасная демонстрация потока данных**, а не уязвимое XSS-задание:
сервер экранирует HTML, клиент использует `textContent`, бот посещает страницы
анонимно. Демо-профиль открывается через отдельный учебный вход с HttpOnly-cookie.
Намеренного выполнения внедрённого HTML и выдачи привилегированной cookie боту нет.

CTFd, release-скрипты и существующий форум `tasks/xss` не изменены.
Прототип не входит в аудит действующего production-релиза в `ops`; для него есть
отдельные проверки в `test/`.

## Запуск

Нужен запущенный локальный Docker Engine с Linux-контейнерами. Из корня репозитория:

```powershell
Copy-Item tasks/kb-search/.env.example tasks/kb-search/.env
docker compose --env-file tasks/kb-search/.env -f tasks/kb-search/compose.yml up -d --build --wait
```

Если `.env` уже существует, сохраните его. В примере находятся только публичные
демонстрационные значения. Первой сборке нужны базовый образ Playwright и npm-пакеты
из реестров либо их локальный кэш.

Приложения доступны только через loopback:

| Приложение | Адрес | Передача запроса |
| --- | --- | --- |
| REFLECTED | http://127.0.0.1:18084 | `/search?q=браузер` → сервер |
| DOM | http://127.0.0.1:18085 | `/search#q=браузер` → JavaScript в браузере |

Для сравнения откройте вкладки Network и Elements в инструментах разработчика.
У REFLECTED запрос и результаты находятся в HTTP-ответе. У DOM fragment не
передаётся серверу, и результаты формируются клиентским скриптом. Сервер DOM
игнорирует также query-параметр `q`, возвращая одинаковый HTML страницы `/search`.
Пустой запрос показывает каталог; неизвестный запрос — «Ничего не найдено».

Форма «Отправить ссылку модератору» принимает только абсолютный URL `/search`
соответствующего публичного origin. Query и fragment сохраняются при замене
origin на `http://127.0.0.1:8080` **внутри своего контейнера**. В каждом приложении
своя последовательная очередь: до 8 заданий вместе с активным, не чаще одной
отправки в 3 секунды. Новый контекст браузера создаётся для каждого посещения
и закрывается через 5 секунд после загрузки, в том числе при ошибке загрузки.

Форма показывает результат приёма, а не завершения посещения. Операционные
счётчики бота доступны в `/healthz`: `queued`, `active`, `completed`, `failed`.
URL, запросы, содержимое страниц и cookie не логируются и не публикуются.

Демо-вход находится в `/profile`; используйте значение `DEMO_LOGIN_CODE` своего
приложения из `.env`. Сессия действует 10 минут. Без cookie, с поддельной,
просроченной или выданной другому приложению cookie профиль возвращает 401.
Флаги имеют вид `KB2CTF{demo_kb_...}` и различаются у двух приложений.

## Ограничения контейнеров

У каждого приложения собственная сеть `internal: true`, без IPv6 и без общего
сетевого интерфейса со вторым приложением. Публикуется только один порт на
`127.0.0.1`. Постоянных томов и bind mounts нет.

Бот разрешает только GET-запросы к `/search`, каталогу и двум статическим файлам
своего приложения. Перенаправления не выполняются; WebSocket и service workers
блокируются. Заголовки Cookie/Authorization не отправляются, Set-Cookie от
посещаемой страницы отбрасывается. Chromium работает с включённой песочницей;
seccomp-профиль скопирован из существующего бота, оригинал не изменён.

Для каждого контейнера заданы: UID/GID 10001, read-only rootfs, `cap_drop: ALL`,
`no-new-privileges`, лимит 256 процессов, 768 MiB RAM, 1024 MiB RAM+swap, 1 CPU,
128 MiB shared memory, ограниченный `/tmp`, файловые дескрипторы и ротация логов.
В этой первой версии нет release-инструментов, host firewall/systemd-настройки
и автоматической проверки свободных ресурсов перед запуском.

Остановка и удаление только этого Compose-проекта:

```powershell
docker compose --env-file tasks/kb-search/.env -f tasks/kb-search/compose.yml down
```

## Проверки

Эти тесты не запускают Docker-контейнеры и не требуют установки Playwright
в рабочую директорию. Нужны Node.js 24, Python 3 и Docker Compose CLI:

```powershell
node --test tasks/kb-search/test/*.test.js tasks/kb-search-bot/test/*.test.js
python -m unittest discover -s tasks/kb-search/test -p 'test_*.py' -v
```

Проверяются одинаковый поиск, кириллица, экранирование, независимость DOM-ответа
от `q`, сессии, форма отправки, границы URL, сериализация и восстановление очереди,
закрытие контекстов и запрет перенаправлений. Контексты Playwright в этих тестах
заменены тестовыми объектами. Проверки Compose читают нормализованную конфигурацию.

Это не заменяет запуск настоящего Chromium в контейнере. После запуска отправьте
из каждой формы собственную ссылку `/search`, подождите и убедитесь в росте
`bot.completed` без `bot.failed` в `/healthz`. Фактическая сетевая изоляция,
совместная нагрузка и отсутствие OOM требуют отдельной проверки при работающем
Docker Engine; эти свойства нельзя считать подтверждёнными только по unit-тестам.
